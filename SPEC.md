# SPEC.md — what to build (owner → manager)

This is the **only source of requirements**. The manager reads it at the start of every cycle.
You (the owner) change the project in either of two ways, and the manager treats them the same:

1. **Edit this file** (and answer approval requests in `plan/APPROVALS.md`), or
2. **Use the buttons on the report site** (R-001): *New requirement*, *Change*, *Remove*, *Ask a question*, and *Approve / Deny* on pending decisions. Each button is a plain link that opens a **pre-filled GitHub issue** on `cia1099/cloud_home`; you press *Submit new issue* (works from a phone). The site itself stays read-only.

The manager reads open issues **authored by `cia1099` only** (R-050), merges them into this file, replies on the issue and closes it. Anything from anyone else is ignored — the repo is public, so strangers can open issues; they never count as requirements or approvals.

## How to change requirements

Add / change / remove a row in section 3, or add a line to section 6. The manager treats these as binding.

| You write | Meaning |
|---|---|
| `ADD` a new row | New requirement. Give it an `R-` id (or leave blank, the manager assigns one). |
| `CHG R-012: …` in the Notes column | Change an existing requirement. The manager updates the row and re-opens it if it was `done`. |
| `DEL R-012` | Remove it. The manager marks it `dropped` (rows are never silently deleted) and stops work on it. |
| Priority `P0` must · `P1` should · `P2` nice | Work is taken P0 first. |
| Status `todo` · `doing` · `review` · `done` · `blocked` · `dropped` | Managed by the manager. `blocked` always states what is needed and from whom. |

Write acceptance criteria as things that can be checked ("uploading a 2 GB file shows progress and can be cancelled"), not wishes.

## 1. Product

**Cloud Home** — a family cloud-storage service replacing Google Drive, running on a home device with an
external drive. Rust backend (done: accounts, files/folders, trash, shares, search, batch download,
previews, SSE live events, usage, admin, online self-update foundation), plus a web UI (to build).
Ships as a packaged device that updates itself over the internet from GitHub Releases.

## 2. Standing decisions (from the owner)

- **Team:** manager, backend engineer, frontend engineer, designer, tester. Backend and frontend are separate people.
- **Frontend stack:** Vite + React + TypeScript single-page app, no SSR, **no SEO requirement** (README.md).
- **Languages:** the product UI supports **English, Simplified Chinese (简体中文, `zh-Hans`) and Traditional Chinese (繁體中文, `zh-Hant`, Taiwan-standard wording)**. The report site is English + 简体中文 only.
- **Private by default (2026-11-23):** new accounts must be **approved by an administrator** before they can use the drive. Registration modes `open|approval|closed`, default `approval`; the very first account is auto-approved (empty user table, local/private caller only). Approval is done through the private admin endpoints and through a chat app (provider-neutral design, Telegram first). Design in `spec/admin_chat.md`. The resulting breaking change to `POST /auth/register` is **approved by the owner**.
- **All-in-one box (2026-11-24):** one `cloud_home` binary serves both the API and the web UI from the same origin, for the owner's family and friends only — the UI is not public and has no SEO needs. The **UI is part of the product version and part of every update**: an update replaces backend and UI together, atomically, and rolls back together.
- **Interruptions are expected (5-hour usage limit, 2026-11-24):** everything the team knows lives on disk, not in a session. The manager keeps `Active tasks` in `plan/STATUS.md`, workers commit early on task branches, and a fresh session resumes from those notes and git (never `--resume`). The team defaults to one worker at a time to spare the shared allowance. `scripts/run_manager.sh -p` waits for the limit to reset and restarts the manager automatically.
- **Look:** Apple web style, as clean as possible, like iCloud. The designer must use the `apple-design` skill.
- **Autonomy:** the team may build, test and commit locally. **Publishing reports to the report server is pre-approved** (`scripts/deploy_report.sh`, which replaces `~/report_web` on `berton.home`, keeping the previous version as `~/report_web.prev`). It must **ask (via `plan/APPROVALS.md`) before**: pushing, tagging, releasing, deploying anything else, changing keys/secrets, breaking API changes, costly or restrictively-licensed dependencies, deleting data or features.
- **Commits:** local only, on `agent/<R-id>-<slug>` branches, no AI attribution lines in commit messages.
- **Reporting:** the manager reports through a website it builds (R-001) and publishes to https://report.cia1099.cloudns.ch; reports contain real screenshots and animations of the running product, written in English and Simplified Chinese. The owner expects these reports to be genuinely impressive.
- **Report site tooling:** bun + Vite, like the owner's sample project (`bun create vite`, vanilla TypeScript).
- **The report site is public, with no login, and nginx is not to be changed.** Nothing sensitive may ever be published (see R-001).
- **Owner requests arrive as GitHub issues** created from buttons on the site (R-001) or typed by hand; only issues authored by the owner are acted on (R-050).
- **Live demo of the UI: deferred** until the UI is complex enough to warrant it. The `/product/` page shows screenshots and recordings only.

## 4. Out of scope (do not build)
Native mobile/desktop apps; multi-device sync clients; collaborative document editing; payments; third-party storage backends; any hosting of other people's data.

## 5. Constraints

The manager reaches the report server only through `scripts/deploy_report.sh`, using the owner's existing SSH access to `berton.home` (key-based, no password in any file). Any other credential the team needs is placed by the owner in `~/.config/cloud_home/` — never in chat, never committed, never published.
